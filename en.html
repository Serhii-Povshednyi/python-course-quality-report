Mutation Testing — Do the Tests Actually Catch Bugs

A coverage percentage only answers "did this line execute at least once," not "would a test notice if this line broke." Mutation testing answers the second question directly: a tool deliberately injects thousands of small, individual defects into the code (flips < to <=, && to ||, removes a bounds check, and so on) and checks whether at least one test then fails. If no test catches the injected defect, that's a real gap — even when line coverage itself reads 100%.

"Caught" here means a mutant either turned at least one test red, or caused an infinite loop/hang (also counted — the defect was still unambiguously flagged, just by a different signal). Every individual case where a mutant initially survived was reviewed by hand: either a new test was written that documents the real behavior, or it was mathematically proven that the specific code change can never affect the outcome at all — and in that case, the line itself carries a comment explaining why, not a silent pass.

Methodology — Code Correctness (CPython Cross-Check)

Three independent tracks, sharing no code and with no dependency between results. Interpreter: the app runs a custom, from-scratch Python interpreter (not CPython, not a third-party library) — every reference solution, template-generated instance, and randomly generated program was run simultaneously through the app's interpreter and a system-installed CPython 3.12.3, then compared for an exact result or error-consistency match. Curriculum structure: a full, non-sampled pass over every content file. Spaced-repetition scheduler: its output checked against a separately written implementation of the same formula. Validation ran through a temporary, isolated tool kept outside the app's own code, in several independent rounds run without referencing each other's results in advance.

How These Numbers Were Actually Reached — No Gloss

These figures aren't where things started. The first mutation-testing pass on the largest, hardest module (the Python interpreter, ~2,500 lines) came back at 75.65% — roughly a quarter of the deliberately injected defects went completely unnoticed. Closing that gap to 100% took seven consecutive passes, each one closing part of the remainder while surfacing new edge cases — including methodology mistakes made along the way, during the checking process itself.

Real application bugs found and fixed (not just test gaps) — surfaced specifically by this thorough process: lesson scores were being wrongly deflated after a corrected mistake (one wrong answer capped the maximum possible score, even if the learner immediately got the retry right); the placement test was wrongly granting the "Flawless Run" and "No Mercy" achievements for lessons that were skipped, not genuinely completed; and three narrow interpreter bugs (integer division, remainder-operator rounding, bool-vs-int comparison).

One methodology mistake was caught and corrected mid-process: an intermediate verification approach (replacing an entire line of text instead of mutating at Stryker's exact coordinates) overcounted how many mutants were truly "equivalent" (i.e., unfixable) — of 35 such assumptions, only 1 held up. Fixed by switching to precise, coordinate-level verification for every individual case.

The last 5 mutants (string comparison used by list sorting) resisted both a proof of equivalence and a test written through the normal public interface — JavaScript's own sort algorithm makes redundant comparisons that mask a single wrong pairwise result. Resolved by testing the internal comparison function directly, bypassing the third-party sort algorithm's unpredictable behavior entirely.

Bottom line: no number in this report is painted on. Every one is the result of iterative, verified work — including admitting and fixing our own mistakes along the way. That's exactly why these figures can be trusted: the app doesn't just behave correctly on the examples that were checked — the test safety net around it genuinely catches future regressions, rather than just formally existing.

Notes

During iterative validation, three narrow interpreter bugs were found and fixed — none ever affected real curriculum content, and all three are now locked in place by permanent tests that make sure they never resurface:

  • whole-number division printing as an integer instead of Python's actual decimal-typed result (11 instead of 11.0);
  • a rare floating-point rounding artifact in the remainder (%) operator on fractional operands;
  • bool not comparing as numerically equal to int in ==/!=/in/list.remove().

The spaced-repetition scheduler's maximum-interval cap correctly engaged in several hundred steps designed to reach it, with no exceptions. The results above are from the final, most recent pass, run with no known open issues.
